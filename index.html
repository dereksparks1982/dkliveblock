Block ads and trackers

An ad can be a network request, a block of page content, a sponsored social post, or part of a video stream. Blocking one kind does not automatically block the others.

What happens when a page loads

A page asks your browser to load its own scripts, pictures and styles, but it can also contact advertising networks, measurement companies and social platforms. Some requests fetch visible advertising. Others measure visits or conversions without displaying anything. A tracker is not necessarily an advertisement, and a request to a familiar domain is not proof of tracking.

How DK Live Block handles it

Network filtering checks eligible requests against rules from bundled filtering and optional lists such as EasyList and EasyPrivacy. Cosmetic filtering hides certain page elements after the page is drawn. The dedicated Facebook scanner looks for sponsorship evidence, while site-specific media techniques address some video ads. Different tools are needed because the delivery methods differ.

Understand the evidence

A rule match shows why DK chose to block a request, not necessarily who owns the destination or what data it would have collected. Inspect the request type, destination hostname, matching rule and site exceptions. A visual sponsored label is stronger evidence of an ad than a generic CSS class such as ‘card’.

What can go wrong

The same domain or script may serve both useful content and advertisements. Broadly blocking it may damage sign-ins, page controls, videos or shopping carts. Some ads are delivered as ordinary first-party content and cannot be safely separated from genuine posts without more evidence.

Try this

Open the extension's Network Monitor on a familiar site. Compare one blocked request with one allowed request, then read the rule evidence. Avoid changing a rule until you know which page feature depends on it.

Stop unwanted popups

Some advertising does not occupy space on the original page. It attempts to open a new tab, hijack a click, or send you somewhere you never intended to visit.

Popup versus popunder

A popup opens another window or tab in front of your browser. A popunder opens behind it, sometimes so you notice only much later. A deceptive redirect may use a click or scripted navigation to move you to a completely different website.

Why this matters

Unwanted pages often promote subscriptions, fake download buttons, misleading security warnings, or aggressive offers. The danger is not just inconvenience: deceptive pages can try to persuade visitors to install software or disclose credentials.

How DK Live Block handles it

The extension uses navigation and popup signals to help stop unrequested tabs and selected redirect patterns. It also supplies site-scoped protection settings and temporary allowances when the visitor genuinely wants a new tab opened. It does not promise to catch every navigation trick.

Real links must still work

A bank's authentication handoff, a document download, or a checkout window may legitimately create a tab. If a protective rule gets this wrong, a temporary exception is safer than disabling protection across the entire browser.

Try this

If a site opens an unwanted tab, inspect the blocked-popup activity and destination before allowing it. If a legitimate button fails, try a narrow site exception, not a global allowlist.

Inspect and control requests

Your browser makes dozens or hundreds of network requests. DK's request tools are intended to show decisions rather than hide them behind a mystery counter.

What counts as a request

A request might load an image, font, script, video segment, API result or tracking pixel. A single page often calls multiple companies' servers. The destination hostname, resource type and initiator give useful clues, but a hostname alone does not establish the service's purpose.

Allowed does not mean trusted

An allowed request may be necessary for the site, simply unmatched by a filter, or intentionally permitted by an exception. A blocked request may be advertising, tracking, malicious, or occasionally a false positive. Neither outcome is a definitive moral or security judgment.

Evidence before decisions

Where available, DK shows the matched rule, its source or filter subscription, the request category and site context. You can investigate the owning organization separately when credible evidence exists. Registrar details, CDNs and inferred ownership should be labeled as uncertain.

User controls

For eligible requests, DK offers site-scoped Allow/Block controls. Temporary and narrowly scoped decisions reduce the chance of breaking other websites. Diagnostic exports can help explain missed ads or broken pages, but review files before sharing them because even hostnames may reveal browsing interests.

Try this

Find one blocked advertising-related request and one permitted site asset. Read their resource types, then look for the exact rule or exception before deciding whether either needs a manual toggle.

Choose what stays

Good protection needs a brake pedal. Users should be able to reverse a block without permanently disabling the rest of their privacy tools.

Site pause and allowlisting

A temporary pause stops selected protection for a limited browsing session. A site allowlist is a more durable exception. They solve different problems: use temporary controls when investigating a broken page, and permanent exceptions only for sites you genuinely trust.

Hide an element yourself

Block Element lets you choose a visible region and hide it using cosmetic filtering. That's useful for annoying panels, but it does not necessarily prevent the underlying request from happening. Removing something from view is not the same as preventing tracking.

Cookie notice rejection

Some sites ask for permission to use optional cookies. DK can try to activate a site's own Reject or necessary-only control, when available. A consent-banner click is not the same as a per-cookie browser firewall, and a website may ignore the decision.

Distraction cleanup

Newsletter prompts, overlays and other page clutter can sometimes be hidden independently from network blocking. These controls should avoid affecting sign-in forms, navigation or accessibility features. Keep exceptions as narrow as possible.

Try this

If a site breaks, first pause the relevant feature for that site and reload. Re-enable it once you identify the issue, rather than leaving the whole browser unprotected.

How ads reach you

Modern advertising uses several delivery routes. That is why one filter rule cannot defeat every ad on every website.

Network-delivered ads

A page may request an ad script, an iframe, an image or a video resource from a separate advertising service. Network filtering can prevent some of these requests before they arrive, provided the request is recognizable without breaking ordinary content.

First-party and native ads

A social network may send sponsored posts through the same first-party API used for normal posts. Facebook uses GraphQL endpoints for many page operations. The presence of GraphQL is not itself advertising: an ad must be identified by reliable markers in an expected response shape.

Client-inserted versus server-inserted video

Sometimes a player inserts ad breaks using distinct media requests. Other times advertising is stitched into the same stream as the program. A blocked URL, a visible Sponsored label and an ad-break marker are different kinds of evidence, with different limits.

How DK responds

DK combines network filtering, cosmetic cleanup, page-specific recognition and experimental response analysis. The Facebook GraphQL response filter is currently an opt-in development feature, disabled by default until real Firefox testing confirms it preserves normal features.

Try this

Compare an ad shown as a labeled social post with a separate sidebar banner. Ask what evidence reveals each one, and why a rule for the banner might miss the feed post.

Cookies and tracking

Cookies are small pieces of browser-stored state. Some are essential to signing in; others help analytics or advertising systems recognize a visitor.

Useful cookies

A website may store a session identifier to keep you signed in, remember a language choice or maintain a shopping cart. Deleting or denying these without checking their purpose can break important functions.

Tracking cookies

Some cookies and other browser identifiers help measure visits, advertising clicks or repeated activity. Third-party requests are one route to cross-site tracking, but privacy risks can also arise from first-party analytics and non-cookie techniques.

How cookies are created

A server can send a Set-Cookie response header, and page JavaScript can create accessible cookies. Browsers may also partition cookie storage by top-level site, and some cookies are marked HttpOnly or Secure. These details affect what an extension can actually observe or prevent.

Agent Nesty's role

DK's numbered Agent Nesty watchers are designed to wake on particular events. The HTTP observer can record minimized metadata about attempted cookie sets without retaining sensitive cookie values. A recorded attempt does not prove that the cookie was stored or blocked. Browser-level per-cookie Allow/Block enforcement is still under development.

Try this

Look at a site's consent options and ask which cookies are essential versus optional. If you inspect cookie metadata, avoid sharing values or session tokens. Those can effectively act as login credentials.

Install in Firefox

Install for testing in Firefox

To try the latest development source in desktop Firefox:

  1. Get the current source from the GitHub repository (Code → Download ZIP), extract it, or update your existing local checkout. The separate Google Drive ZIP may be an older test upload.
  2. In Firefox, visit about:debugging.
  3. Choose This Firefox and Load Temporary Add-on.
  4. Open the extracted folder, then choose src/manifest.json.
  5. Use the DK Live Block toolbar icon to inspect blocking and adjust optional settings. A separate filtering engine download is not required.

This is a temporary Firefox developer installation; it normally ends when Firefox restarts. The source ZIP is not a signed XPI. The separate unsigned XPI is intended for development testing, not permanent installation in standard Firefox.
